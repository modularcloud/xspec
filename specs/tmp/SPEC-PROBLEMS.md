# SPEC problems

## 2026-09-29 — SPEC 6.5: a file move can require an import specifier no string literal can spell (Phase 10 compliance review, SPEC §1–6)

**Contradiction.** SPEC 6.5 ("Import edits") has the file form rewrite every importer's specifier "the quote style kept (6.4), with the canonical relative spelling of the designated source's post-operation path", and 2.4 reads every specifier as spelled (no escape interpreted). But a valid source path may contain characters that literal cannot carry: 14.19 bars only `#`, U+FFFD, invalid UTF-8, and a missing `.mdx`, and 12.0 accepts any valid-UTF-8 argument value, so a destination such as `specs/q"x.mdx`, `specs/q"x'y.mdx`, `specs/a<LF>b.mdx`, or `specs/a\uzz.mdx` is a valid destination. For an importer using `"`, the kept-style rewrite of a path containing `"` is not a well-formed literal. A path containing both quote characters, CR, or LF has no literal spelling at all. A path containing `\u`, `\x`, and similar sequences not followed by valid hex digits is not derivable under ECMAScript or TypeScript. In each case the importing spec or code source stops being well-formed (14.20). No refusal reason in 6.5 or 14 covers this. `refused-invalid-rewrite` applies to the section form only, and `refused-invalid-destination` covers group membership, extension, segment spelling, and obstructed components. Yet 6.5 says: "These refusals keep every successful move's finishing regeneration (6.4) on a valid workspace — its files well-formed … so it cannot fail for any validation reason", and says the relocation keeps "all references" resolving. So for these destinations SPEC requires a successful move that cannot produce a valid workspace. No product can satisfy both.

(The section form is consistent: an added declaration is spelled `"…"`, and 6.5's admissibility rule then admits no offset for an unspellable specifier, so the move is `refused-invalid-rewrite`. The product's departure there is reported as a product gap, not here.)

**Observed product behavior (head 9d095d9).** Workspace: `specs/A.mdx` = `<S id="a">`, `A`, `</S>`; `specs/B.mdx` = `import A from "./A.xspec"`, blank line, `<S id="b" d={A.a}>`, `B`, `</S>`; optional `src/app.ts` = `import A from "../specs/A.xspec"` plus a marker `A.a`.
- `xspec move specs/A.mdx 'specs/q"x.mdx'`: exit 0, and B's specifier is rewritten to `'./q"x.xspec'`. The product switches the quote style, which 6.5 does not allow.
- A destination containing both `"` and `'`, or CR or LF: `move` and `move --preview` exit 70 with "xspec internal error: the string value … has no verbatim string-literal spelling (SPEC 2.4)" and a stack trace (`jsStringLiteral`, `src/core/edits.ts`). Nothing is modified.
- `xspec move specs/A.mdx 'specs/a\uzz.mdx'`: exit 1. The report holds 14.20 findings on `specs/B.mdx` and `src/app.ts`, which come from the product's post-move re-validation. These are numbered conditions reported as the refusal of a valid workspace, and no 6.5 refusal reason covers them. Nothing is modified.

**Needed.** A SPEC decision for destination paths that an importer cannot spell. Options include a refusal reason, for example extending `refused-invalid-destination` or `refused-invalid-rewrite` to the file form and locating the importers' specifiers, or permitting the other quote style where it spells the path. The same decision should settle the section form's double-quoted added declaration. The ruling on 6.5's automatic-semicolon-insertion import removal (AGENTS.md "Known SPEC 6.5 gap") is a related but distinct case.

**Resolution (2026-09-29, Phase 4 round 1).** Resolved by narrowing valid spec-source paths, as 1.4 already does for ID segments so every rewritten spelling is verbatim in every form: 7.1 now requires a spec-group file's workspace-relative path to contain none of `"`, `'`, `\`, U+000A, or U+000D, and 14.19 reports one that does. Every canonical specifier spelling of a spec source is therefore a well-formed literal in either quote style whose value is the same read verbatim or by TypeScript (which also restores 13.1 for consumers). A file-form destination or created target file containing such a character is `refused-invalid-destination` (6.5, 14), an argument being able to spell each of them. The valid-workspace precondition covers every other designated source, the moved file's own targets included, so no per-specifier refusal is needed. The file form keeps its quote style, and the section form's double-quoted additions and created-file composition are exact. 6.5's closing guarantee names the property. This file stays until the refinement halts.

**Resolution completed (2026-09-29, Phase 4 round 5).** Round 1's bar missed two characters: TypeScript 5.0 through 5.2 reject U+2028 and U+2029 in a string literal of either quote style (5.3 onward accept them), and 14.20 fixes well-formed TypeScript only as what 5.0 accepts. Under 5.0 the characters that break or alter a string literal are exactly U+000A, U+000D, the delimiting quote, `\`, U+2028 and U+2029. 7.1, 14.19 and `refused-invalid-destination` (6.5) now bar U+2028 and U+2029 beside U+000A and U+000D, so every canonical specifier spelling is a literal 5.0 accepts; 1.4 bars both from ID segments (and so tags), so the computed-access spelling a rename or move writes for a segment is one too.

**Note (2026-09-29, Phase 4 round 7).** 14.20 now pins TypeScript at release 5.9.3 alone, which admits U+2028 and U+2029 in a string literal of either quote style. The bars in 1.4, 7.1, 14.19 and `refused-invalid-destination` (6.5) are kept, with the TypeScript 5.0 rationale dropped from 1.4 and 7.1. Every canonical specifier spelling therefore stays a literal that is well-formed under 5.9.3 and ECMAScript 2024, and whose value is the same read verbatim or by TypeScript tooling (13.1). The resolution above still holds.
