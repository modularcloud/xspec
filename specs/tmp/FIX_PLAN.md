## Task 151 — Chain rewrites replace only the tokens they change: whitespace, comments, and line breaks inside a reference stay (SPEC 6.4, 6.5, 2.4, 14.20; A1)

**Requirement.**
- SPEC 6.4: "Rewrites are minimal in-place edits, preserving each reference's quote style and access form (2.4); where a form cannot be kept — a chain segment whose new name is not a valid TypeScript identifier (1.4), or a reference converted between local and imported form (6.5) — the rewritten part uses dot access for segments that are valid TypeScript identifiers, double-quoted computed access for segments that are not, and double-quoted string literals …".
- SPEC 6.5: the moved subtree is "re-identified by prefix replacement of `<id>` with `<new-id>`", and "Beyond these edits, the identity and reference rewrites of this section, and the finishing regeneration, a move changes no bytes."
- TEST-SPEC applies the same reading to both operations: T6.4-2 — "untouched reference parts are preserved byte-wise; only the affected parts change", each rewritten file "byte-equal to an expected file differing from the original in the rewritten segments alone"; T6.5-7 applies it to a move's prefix re-identification. No suite test stages trivia inside a chain, so nothing pins the present behaviour.
- So a chain rewrite replaces tokens only: a segment kept in its form has its name token (identifier, or index literal with its quotes) replaced; a dot segment that must become computed access has its `.` token and its name token replaced; a prefix replacement that changes the segment count also adds or deletes whole accesses. Every whitespace, comment, and line-terminator byte between a chain's tokens — the root, each `.` or `[`, each name or index literal, each `]` — stays where it is, byte for byte. Each rewritten file must stay well-formed (14.20): SPEC gives the reference rewrites no refusal (6.4: every rewritten reference resolves by construction; 6.5's `refused-invalid-rewrite` covers only the origin deletion, the target insertion, and the parent rewrite).
- Out of scope: a reference converted between local and imported form (6.5) is rewritten whole — SPEC 6.4 names it a form that cannot be kept, and a string literal has no room for a chain's trivia (`renderChain` and `chainSpan` callers in `src/core/move.ts`).

**Observed** (A1, at `6034904`; every staging in an `E6_CONFIG` workspace):
- R1, a rename to a non-identifier, MDX (`g010.json`): `specs/A.mdx` = `<S id="a">` LF `A` LF `<S id="a.b">` LF `B` LF `</S>` LF `</S>` LF; `specs/M.mdx` = `import A from "./A.xspec"` LF LF `<S id="m" d={[A /* c */ .a, A` LF `  .a` LF `  .b]}>` LF `M` LF `</S>` LF. After `rename specs/A.mdx a x-y` the `d` value is `d={[A["x-y"], A["x-y"]` LF `  .b]}`: the comment ` /* c */ `, and the line break and indentation before `.a`, are gone. `rename specs/A.mdx a z` (`g011.json`) keeps every byte but the name: `d={[A /* c */ .z, A` LF `  .z` LF `  .b]}`.
- R2, the same rename in TypeScript (`g010.json`): `src/c.ts` = `import A from "../specs/A.xspec"` LF `A` LF `  // note` LF `  .a` LF `  .b` LF becomes `…` LF `A["x-y"]` LF `  .b` LF, the `// note` line deleted. Likewise `A . a` → `A["x-y"]` and `A./* c */a . b` → `A["x-y"] . b`. `rename … a z` changes the name only.
- M1, a section move whose prefix replacement adds a segment (`m019.json`): `specs/O.mdx` = `<S id="p">` LF `P` LF `</S>` LF `<S id="x">` LF `X` LF `<S id="x.y">` LF `Y` LF `</S>` LF `</S>` LF; `src/c.ts` = `import O from "../specs/O.xspec"` LF `O /* keep */ . x` LF `O` LF `  // note` LF `  .x` LF `  .y` LF. `move specs/O.mdx#x specs/O.mdx#p.x` gives `O.p.x` LF `O.p.x` LF `  .y` LF. MDX `d` chains behave the same, and so does a cross-file move into a deeper ID (`m016.json`: `O /* keep me */ .x` → `T.u.x`); a move that only re-roots the chain keeps the trivia (`O /* c */ . x` → `T /* c */ . x`).

**Location.**
- `classifyReference` in `src/core/references.ts`: each `ClassifiedSegment`'s `accessSpan` starts at `node.expression.getEnd()` — the end of the preceding chain element, so it spans the trivia before the `.` or `[` — and ends after the name or `]`; `nameSpan` is the name token alone. Both the MDX analyzer (`chainReference` in `src/core/spec-references.ts`, through the span translator) and the code analyzer (`src/core/code-analysis.ts`, through `spanRange`) copy these into `SegmentSpelling` (`nameRange`, `accessRange`).

- `chainPrefixEdits` in `src/core/move.ts`: with equal segment counts it applies `segmentEdit` per changed segment; otherwise it re-renders the whole prefix over `segments[0].accessRange.start` … `segments[count - 1].accessRange.end` (`renderAccess`). Its three callers (two spec-source paths and the code-source path) add each returned edit and report one `reference-rewrite` per occurrence to the preview.
- Already minimal, keep as they are: name-only edits (`nameRange`) and root-only re-rooting (`rootRange`).

**Change.**
1. Record where each segment's own access token starts: the `.` of a dot access, the `[` of a computed access, past the trivia that follows the preceding element. Take it from the compiler's tokens, never a hand scan that could misread a comment: the `.` token ends at the name node's full start (`node.name.pos`) and the `[` token at the index's (`node.argumentExpression.pos`), each token one character (a `?.` makes the chain dynamic, 2.4); `getChildren(sourceFile)` gives the same tokens. Add it to `ClassifiedSegment` (a token span, or a start offset), carry it into `SegmentSpelling` through both builders, and correct the doc comments of `accessSpan`/`accessRange` (or redefine them to start at the token, checking every user: `chainSpan` uses only `accessRange.end`).
2. `segmentEdit`: a dot segment converted to computed access replaces its `.` token with `[` and its name token with the double-quoted literal followed by `]`, leaving the bytes between them as they are — `A /* c */ .a` → `A /* c */ ["x-y"]`, `A./* c */a` → `A[/* c */"x-y"]`. Two edits, or one edit from the `.` through the name whose replacement re-emits the bytes between verbatim; returning several edits means `segmentEdit` returns `SourceEdit[]` and both callers add each. A kept form is unchanged (name token only).
3. `chainPrefixEdits`, when the counts differ: pair old prefix segment `i` with new prefix segment `i` from the root (`i` below the smaller count) and edit each pair as the equal-count path does (`segmentEdit` where the names differ).
   - New prefix longer: insert the extra new segments, rendered by `renderAccess` (the present form for added segments), immediately after the last paired old segment's last byte (its name, or its `]`) — a zero-length edit, or folded into that segment's own edit. `O /* keep */ . x` → `O /* keep */ . p.x`; `O` LF `  // note` LF `  .x` LF `  .y` → `O` LF `  // note` LF `  .p.x` LF `  .y`.
   - New prefix shorter: delete each extra old segment's access from its own `.` or `[` token through its last byte (what lies between its tokens goes with it), keeping the trivia before that token. Where a deletion leaves the line it was on holding nothing but whitespace — in a spec source, nothing but whitespace and its container prefixes, such as a block quote's `>` — delete that whole line, its line terminator included. **Design** (this plan's choice; the acceptance criteria under Verification bind, so a different design meeting all of them is acceptable — say why in the commit message):
- The tables are fixed when the session file is created. The write that creates it (`review create`) builds `references`, `states`, and `texts` exactly as format 2 does today (same traversal, same index runs, same sizes); every later write stores them byte for byte unchanged — no entry appended, reordered, or dropped, even when no item names it any more. A position in a table no write can change is a stable key: every copy of the session on every branch holds the same table, and no write assigns a position.
- Whatever an item records later that the tables lack — a reference first met after creation (a node joining the item's context, scope, or origin), a node state (hashes or presence after an edit, 10.4), a snapshot text (10.7) — is stored inside that item's own entry: for example item-local `references`, `states`, and `texts` members, omitted when empty, in first-use order within the item, named from the item's lists by a token form distinct from shared-table indices (or by indices past the fixed table's length). Prefer keys naming what they record (the node) wherever that costs nothing; positions within one item are acceptable, because every write rewrites an item's entry whole. A `no-change` or `skipped` resolve then changes nothing outside the resolved item's entry (and `journalLength` when the journal grew); an `updated` resolve's re-derivation and a `split` change exactly the items they add or reassign (plus `nextItemId` and, for `split`, `decompositions`).
- Earlier formats: a format-2 file's tables are kept exactly as stored, fixed from then on. A format-1 file's tables are built when it is read — the creating traversal over its items as read, never over the session as the write leaves it — so two branches' first writes of one format-1 file store identical tables and differ only inside the items each changed. Set `ReviewSession.tables` that way at read; correct its doc comment ("whose write starts the tables afresh" no longer holds).
- Store `version` 3; read versions 1, 2, and 3; any other version stays the 14.21 corruption.
- Parsing checks the new members as it checks format 2's tables and lists (well-formed tokens, indices in range, canonical references within `journalLength`, well-formed states and texts, aligned lengths); anything else is the 14.21 corruption.
- Considered and rejected, so you need not retry them: content-addressed shared tables (objects keyed by a digest of each entry) make keep-both meaningful, but both branches' additions still land in one shared object, where git conflicts whenever the new keys sort next to each other or after the last key (whose line gains a comma) — `p008` would merge only by chance; and naming each recorded node by a digest instead of an index run makes every item's lists grow with its node count — about a million node mentions per list kind on the 1,500-deep chain — which breaks the 100 MB bound.
