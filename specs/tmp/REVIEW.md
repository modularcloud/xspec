# Review — specs/patches/0002-config-import-specifier.md — Phase 3 refinement iteration 4: continuing the first refinement of IP 0002 (configuration import not tied to a package name)

## Critical
*none*

## Important
- [I1] Change 2, Reach, "Nothing nearer": this condition does not rule out every resolution TypeScript makes before it reaches the placement. So for some names that N's grammar admits, Reach under TypeScript and the type contract are false. When N's last segment contains a `.` (the grammar allows it: `a.js`, `a.b`, `socket.io`), TypeScript 5.9.3 first strips that segment's extension and tries files at the stem. It does this under `node10` always, and in the other modes outside ES-module lookups whenever the package has no `exports` map. The stripped extension is a recognized one (`.js`, `.ts`, `.d.ts`, `.json`, …) or, failing that, the text from the segment's last `.`. The files tried are `node_modules/a.ts`, `a.tsx` and `a.d.ts` for N = `a.js`, and `node_modules/a.d.b.ts` for N = `a.b`. None of these begins `node_modules/N.`, so the stated condition holds while TypeScript resolves the specifier to the stray file. Probed with 5.9.3 under `strict` and `moduleResolution` `node10`:
  - Package placed at `node_modules/a.js`, plain file `node_modules/a.ts` beside it: `"a.js"` resolves to `a.ts`, and the `defineConfig` call fails with TS2349.
  - N = `a.b` with `node_modules/a.d.b.ts`: the specifier resolves there, with TS6263.

  No product can meet the contract in that state, so the claim "each ruling out a resolution those tools make before they reach the installed package" has to become true. Two ways to do it (the Driver's choice):
  - Widen the condition. For example: in those `node_modules` directories, no entry other than the placement may have a name that begins with N's last segment up to its first `.`, followed by `.`.
  - Take `.` out of N's last segment.
- [I2] Change 2, Runtime (and Reach under Node.js): the runtime contract fixes which Node.js releases it covers, but not how Node.js is run. The TypeScript side, by contrast, pins "every other option at its default". Options and hooks that change resolution can defeat any package:
  - A user condition (`--conditions`/`-C`) makes both `import` and `require` active for every load, so the key an `exports` map lists first wins for both. On Node.js 22.22, with a map listing `require` first, `node -C require` makes an `import` namespace hold `default` and `defineConfig`, which breaks "exactly `defineConfig`". With `import` listed first, `-C import` sends `require` to the ES-module entry, which releases before 22.12 do not load by default.
  - Loader and customization hooks (`--import` registering hooks, `--loader`), and the same settings passed through `NODE_OPTIONS`, can redirect any load.

  Add the Node.js counterpart of the TypeScript pin: Node.js run with no option, environment setting or module customization hook that changes how modules are resolved or loaded. At minimum that means no `--conditions` and no loader or hook.

## Optional
- [O1] Change 2, Reach: the routes listed (a static `import` in an ES module, a dynamic `import()`, `require` in a CommonJS module) are Node.js's. Under TypeScript, a covered setup has only one route: the configuration's import declaration. TypeScript resolves it in require mode in a `.cts` file, or in a `.ts`/`.tsx` file of a CommonJS project. That case is neither "a static import in an ES module" nor `require`, although the type contract covers it. State TypeScript's route separately, so that Phase 4 does not carry over a "TypeScript resolves `require`" reading that no covered setup can test.
- [O2] Change 2, Covered setups, Program: "its package.json declaring "type": "module" or not" should name the nearest `package.json` to the configuration file as the one that decides. It should also say whether a project with no `package.json` is covered (both tools treat such a project as CommonJS).
- [O3] Change 2, Runtime, last bullet: "so it rests on no behavior a later 22.x release introduced, such as `require` of an ES module" is explanation that edges toward implementation guidance. "Every release of the Node.js 22 line" already includes 22.0. Mark the clause as rationale not carried into `SPEC.md`, as the installation rationale already is.
- [O4] Change 3: rather than leaving the example's specifier "settled in refinement", give Phase 4 a test for "names none". A spelling outside N's grammar (Change 2), for example one with an uppercase letter or a `<`, can never be read as an installable package name. Any lowercase bare name can be.

## Open questions
- [Q1] (non-blocking) Under the options TypeScript 5.9.3's own `tsc --init` writes, a CommonJS project cannot type-check `xspec.config.ts`, whatever the module declares (TS1295 under `verbatimModuleSyntax`). The IP keeps the upward search on `xspec.config.ts` alone (Non-goals). Its Documentation section sends those users either to an `.mts` file named with `--config` on every command, or to a project-wide `"type": "module"`. Should the upward search also find `xspec.config.mts`, so that these projects get type support without `--config`? That would take this IP beyond its seed. Tentative read: keep this IP as scoped, since the documented route works, and add `.mts` discovery in a follow-up IP if CommonJS users matter.
- [Q2] (non-blocking) Type support is promised under TypeScript 5.9.3 only (the release 14.20 pins). Editors and `tsc` on later releases (6.x, and the native port) are outside the promise, and the harness would test only 5.9.3. The Developer's goal ("editor and `tsc` type support") reaches whatever release users run. Should the contract name a range of releases? Tentative read: keep the single pin, aligned with 14.20 for testability, and move both together in a later IP.
