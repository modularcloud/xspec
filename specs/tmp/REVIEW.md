## Important
- [I1] Change 2 → Package and installation (the grammar of `N`) and → Type contract: the grammar admits names that TypeScript 5.9.3 reads as replacements for its default libraries, and for those names the type contract is false.
  - **How replacement works.** Unless `libReplacement` is `false`, which neither covered option set sets, TypeScript looks up each default library it loads (`es5`, `esnext`, `dom`, …) as a package named `@typescript/lib-<library>`. When it finds one, it loads that package's entry in place of the library.
  - **The failure.** With the package installed under `@typescript/lib-es5` or `@typescript/lib-esnext` (scope `typescript`, names `lib-es5` and `lib-esnext`, all inside the grammar), a valid covered file fails to type-check: TS2318 "Cannot find global type 'Array'", "… 'Function'", and more. This holds under strict defaults (`node10` and `nodenext`) and under the initialized-project options.
  - **Evidence.** Reproduced with TypeScript 5.9.3 and a stand-in package that type-checks cleanly when installed as `stand-in`, so the failure comes from the name alone.
  - **Fix needed.** The proposal already excludes the `@types` scope and Node.js built-in names on these same grounds, but it lacks the matching exclusion for library-replacement names. Without it, Phase 4 writes a contract that no implementation can meet for names its own grammar admits.
- [I2] Change 2 → Package and installation, → Reach, and → Covered setups (Program): the placement and the program promise resolution in setups where the tools do not perform it, or leave open which path they mean. All three cases below were reproduced with TypeScript 5.9.3 and Node.js 22.22.0.
  - **Ancestors named `node_modules`.** "At `node_modules/N` in the importing file's directory or one of its ancestors" admits an ancestor that is itself named `node_modules`. Example: the configuration in `X/node_modules/proj` and the package at `X/node_modules/node_modules/N`. TypeScript (`node10` and `nodenext` alike, TS2307) and Node.js `require` skip such a directory; only Node's ES-module loader finds the package.
  - **Self-reference.** The program constrains the project's `package.json` only in `type`, and Reach excludes only something else *installed* under `N`. A project whose own manifest names it `N` and declares `exports` captures the specifier by package self-reference, before any `node_modules` lookup. Under TypeScript `nodenext` and `bundler` the import resolves to the project's own entry (TS7016), and both Node.js loaders return the project's exports. The type contract and Reach are both false there.
  - **Physical or logical ancestry.** "Ancestors" does not say which path is read. Node.js resolves from the importing file's physical path, while TypeScript follows the path the root file is named by. Take a project directory reached through a symbolic link, with the package in an ancestor along the logical path only: `tsc` succeeds when the file is named by its logical path, and Node.js fails. 11.6 settles the same question for anchoring by reading physical paths.
  - **Fix needed.** Each case is a SPEC.md-level statement that is false or ambiguous in a constructible setup. The placement, Reach and the program should exclude these cases or pin them down.
- [I3] Change 1 → Reading the file as configuration: two statements are false for escapes that TypeScript 5.9.3's scanner rejects. They are "every spelling is therefore accepted alike … spellings carrying escape sequences" and "a configuration's validity … [is] independent of the specifier's spelling".
  - **The rejected escapes.** `"\x4"` (TS1125), `"\u{110000}"` (TS1198), `"\01"` (TS1487) and `"\8"` (TS1488) are each a syntax error. Under 14.20 a file spelling one is not well-formed TypeScript, so it stays a configuration error (7, 14.14), which the Non-goals keep unchanged.
  - **Consequence.** Carried into SPEC.md as written, the sentence contradicts 14.20, and Phase 4 would have to guess which rule wins.
  - **Fix needed.** Limit the acceptance and the independence to specifiers whose spelling leaves the file well-formed (14.20). Line continuations, U+FFFD and well-formed escapes are unaffected.

## Optional
- [O1] Change 2 → Covered setups → Program: "with no declarations visible beyond TypeScript's default libraries" literally excludes the package's own declaration files, which the contract depends on; Strict defaults even says they "count". Reword it to exclude only declarations other than the default libraries and the package's own (for example, `@types` packages and other packages).
- [O2] Change 1 → The one exception (first sub-bullet), and Interactions → Strict relaxation, say the code-group case "is that source's invalid-import finding (14.15)". Read as the only finding, this over-claims: 4.5 and 14.18, as they stand, decide whether the call through the invalid named `defineConfig` binding is also condition 18. Exit 1 follows either way. Saying the workspace fails with 14.15, rather than that the case *is* that finding, keeps Phase 4 from writing a new exclusivity rule.
- [O3] Change 2 → Reach: the Node.js half names no release range, while Runtime is scoped to the 22 line and later. Read alone, Reach promises `import` and `require` resolution on releases where `import` or `exports` do not exist. Scope Reach's Node.js half to the Runtime's releases so that Phase 4 does not have to infer it.

## Open questions
- [Q1] (non-blocking) Change 2 → Covered setups, and the Documentation section. The type promise is pinned to TypeScript 5.9.3 and to two option sets: strict with every other option at its default, and exactly `tsc --init`'s set. The docs may state type support only on SPEC.md's authority, so they can promise it for that one release and those setups alone. Users' editors and builds run whatever TypeScript release and options their project pins, rarely exactly these. Is that the promise you want users to read, or should the contract name a release range or broader option coverage? Tentative read: keep the pin. It is offline-testable and matches the release 14.20 already fixes, while a range would have to track option changes across releases. The docs can describe other setups as unverified.
- [Q2] (non-blocking) Change 2's initialized-project carve-out and the Documentation section.
  - **The gap.** `npm init -y` (npm 10.9.4) writes no `type` field, so a fresh `npm init` plus `tsc --init` project is CommonJS, and in it TypeScript rejects the import of the default `xspec.config.ts` (TS1295). That is the very setup the recorded goal describes ("a plain `npm install --save-dev …` … get editor and `tsc` type support").
  - **The current remedy.** The proposal meets the goal there only through the docs: rename the file to `.mts` and pass `--config` on every command, or switch the project to `"type": "module"`.
  - **The question.** Should the upward search (7) also find an `.mts` configuration file, so these projects get type support without `--config`? Or is the docs remedy enough for this patch?
  - **Tentative read.** Keep the file name fixed here, as this IP's Non-goals state, and take up `.mts` discovery as a follow-up IP if you want it.
