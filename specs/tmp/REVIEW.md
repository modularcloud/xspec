# Review — specs/patches/0002-config-import-specifier.md — Phase 3 refinement, iteration 2 (after iteration 1's review was applied at 693025f)

## Critical
*none*

## Important
- [I1] Change 2 → **Runtime**, third bullet ("Neither loading the module nor calling `defineConfig` reads or writes anything, accesses the network, or has any other effect"). As worded this cannot hold. Loading a module reads its own files, and Node.js's resolver also reads `package.json` files and follows a symbolic-link install. So the bullet contradicts **Reach**, which requires the module to load, and it is not blackbox-testable as stated. A harness that enforces it literally, for example by denying every filesystem read, leaves the module unloadable, and then no implementation can pass. "Any other effect" also names no observable channel. Fix: limit the rule to what the module does beyond the runtime's own resolution and loading of the package's files. Then name the channels a test observes, both on load and on call: no read outside the package, no write, no network access, no output to standard output or standard error, and no change to the global object or process state.
- [I2] Change 2 → **Package and installation**. "The product is distributed as a package" and "Installing the product under a name `N`" define distribution and installation for the whole product, but everything stated under them concerns the module alone ("Nothing else need be installed: the module's declarations and code …"). The IP does not say whether the `xspec` executable belongs to that package, or whether it must work after such an installation. Such an installation is a bare placement "with no package-manager run, install-time step", so it creates no executable link and installs no dependency. Phase 4 would have to guess. It could invent a distribution requirement for the executable, which no expressed intent supports (the non-goals only keep the command name). Or it could assume none is meant. Fix: scope both definitions to the module's contracts, and state that they make no claim about how the executable is provided or run.

## Optional
- [O1] **Interactions and compatibility** → Strict relaxation: "whose specifier ends in `.xspec` or designates a derived-file path" drops "relative". Change 1 and SPEC 4 both require it. An absolute specifier that designates a derived-file path is not an invalid import (4), so such a file stays valid. Use change 1's wording.
- [O2] Change 1, last sub-bullet: "an import of it ending in `.xspec`" reads as an import *of* the configuration file. Say "its import, when its specifier ends in `.xspec`, is invalid (14.15)".
- [O3] Two phrases are too absolute. In change 2 → Package and installation, "the module's declarations and code reach nothing outside the package". In Covered setups → Program, "with no other declarations visible". Read literally, both exclude TypeScript's default library declarations, which every covered program loads (`noLib` stays at its default) and which any declaration file uses (`string[]` is the library's `Array`). They also exclude the runtime's built-ins. Carve these out: the rule should be that nothing is installed outside the package and no declarations are visible beyond TypeScript's default libraries.
- [O4] Change 2 → the grammar for `N`: "of two spelled `@scope/name`, each segment … beginning with a letter or digit". The first segment, `@scope`, begins with `@`. Say instead that the scope and the name are each such a run.
- [O5] Change 2 → Runtime, first bullet: "a `require` result has that one own enumerable property". Say whether symbol-keyed properties count, so a test knows which enumeration to compare: string keys alone, or every own enumerable key.
- [O6] Change 2 and the non-goals: the contract covers only the package's root entry, and nothing says whether any other path in the package (a subpath or a deep file import) is an interface surface. To match "No programmatic interface beyond `defineConfig`", state that no other module of the package carries a contract.
- [O7] Non-goals, fourth bullet: per Developer (2026-10-28), issue #8 parks all three accepted residuals: the 14.20 syntax-failure location gaps, the 6.5 gap for TypeScript import removals joined by automatic semicolon insertion, and the `Object`-member requirement-path type error. The bullet describes only the last one. Name all three as staying outside this patch, its release included.

## Open questions
- [Q1] (non-blocking) Which runtimes should the module's runtime contract cover? Change 2's Runtime promises loading through `import` and `require` on the Node.js 22 line only. This is SPEC.md's first reference to Node.js, and it goes beyond the recorded goal, which asks only for editor and `tsc` type support. Node.js 22's maintenance support ends in April 2027 and newer LTS lines (24 and later) are current, so the docs could not claim runtime support anywhere else. The options:
  - a floor ("the Node.js 22 line and later"), keeping the rule that the contract relies on nothing a later 22.x release introduced;
  - the lines the product itself supports;
  - 22 alone, as now.

  Tentative read: a floor. Keep a runtime contract at all, since tools other than xspec may execute the configuration file.
- [Q2] (non-blocking) Should the covered setups include what `tsc --init` generates? The type contract covers TypeScript 5.9.3 with `strict` on and every other option at its default. But 5.9.3's own `tsc --init` turns on `declaration`, `verbatimModuleSyntax`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `isolatedModules`, `skipLibCheck` and more, all outside the covered setups. I probed with a stand-in package under those options (TypeScript 5.9.3, ES-module project):
  - A `defineConfig` that returns a configuration type the package does not export, which the "no named configuration type" rule pushes toward, fails every configuration with TS4082 ("Default export of the module has or is using private name").
  - Exporting that type, or returning the argument's own type, passes.
  - In a CommonJS project, TypeScript rejects the declarative import for any product (TS1295) unless the file is `.mts`.

  So a conforming product could break type support in a freshly initialised project, which defeats the goal this patch exists for. Should the covered setups add the `tsc --init` option set for ES-module-format files, or should the "no type" rule be relaxed? Tentative read: add the option set and keep "no type". That forces a return type nameable without an exported type, and keeping 5.9.3 as the one covered release matches 14.20.
