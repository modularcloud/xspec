# Review — specs/SPEC.md — SPEC-PROBLEMS refinement, round 5: file-form specifier rewrites to destination paths an importer cannot spell (6.5)

Logged problem (specs/tmp/SPEC-PROBLEMS.md, 2026-09-29): **resolved for `"`, `'`, `\`, U+000A and U+000D, but not for the other two ECMAScript line terminators, U+2028 and U+2029, in TypeScript importers (see C1).** Everything else in the round-1 resolution holds. A file-form destination or created target file that contains a barred character is `refused-invalid-destination` (6.5, 14). The valid-workspace precondition covers every other designated source. I found no other residual of the logged class (a successful move whose regeneration cannot produce a valid workspace) across the destination, derived-path, exposure, module-linking and write-order cases.

Evidence behind C1 and C2. 14.20 fixes well-formed TypeScript as what TypeScript's scanning and parsing accept at release 5.0: "Every text TypeScript 5.0 so accepts is well-formed, and whether one that only a later release accepts is well-formed is not fixed by this specification." I parsed a one-line import, `import A from "./a<U+2028>b.xspec"`, in both quote styles, and a chain, `SPEC["a<U+2028>b"]`, against stand-alone installs of TypeScript outside the project, and did the same with U+2029. TypeScript 5.0.4, 5.1.6 and 5.2.2 reject every such literal with "Unterminated string literal". TypeScript 5.3.3, 5.4.5, 5.9.3 and 6.0.2 accept them. A string literal holding a raw U+2028 or U+2029 is therefore text that only a later release accepts, and its well-formedness is not fixed by the SPEC. The MDX side is unaffected: ECMAScript 2019 and later, including the ECMAScript 2024 that 14.20 names for ESM blocks and braces, admits both characters in string literals. I also ran every Basic Multilingual Plane code point, plus a few astral ones, through a TypeScript 5.0.4 string literal in both quote styles. The only characters that break the literal or change its value are U+000A, U+000D, the delimiting quote, `\`, U+2028 and U+2029. Adding U+2028 and U+2029 to the characters already barred therefore closes C1 and C2 exactly.

## Critical
- [C1] **Logged problem only partly resolved: spec-source paths may still hold U+2028 or U+2029, which a TypeScript importer's specifier cannot carry under the pinned grammar (7.1, 14.19, 6.5).** The guarantees now assert more than the rules deliver.
  - 7.1 bars only `"`, `'`, `\`, U+000A and U+000D. It then asserts that every canonical specifier spelling, "delimited by either quote character, is a well-formed string literal (14.20) whose value is the same whether read verbatim (2.4) or as TypeScript tooling reads it (13.1)".
  - 6.5's closing guarantee repeats that claim ("its canonical spelling, a well-formed literal in either quote style (7.1)") and concludes that the finishing regeneration "cannot fail for any validation reason".
  - U+2028 and U+2029 are neither barred by 7.1 nor reported by 14.19, and nothing in `refused-invalid-destination` (6.5, 14) covers them. 12.0 lets an argument spell both.
  - Consequence for the file form: a workspace has `src/app.ts` holding `import A from "../specs/A.xspec"`, and the user runs `xspec move specs/A.mdx specs/a<U+2028>b.mdx`. The move must succeed, and it rewrites the importer's specifier to `"../specs/a<U+2028>b.xspec"`. `src/app.ts` is left as text that TypeScript 5.0 rejects. An implementation that reads the 5.0 grammar then meets condition 20 in the finishing regeneration. That is the contradiction the problems file logs, for these two characters.
  - Consequence for the section form: when a TypeScript source needs an added import of a module at such a path, admissibility (6.5), and with it `refused-invalid-rewrite`, turns on the same unfixed question. The move's outcome is therefore not fixed either.
  - Needed, for example: bar U+2028 and U+2029 in 7.1, 14.19 and `refused-invalid-destination` beside U+000A and U+000D, so that all four ECMAScript line terminators are barred. Alternatively, fix the grammar question for these characters. Either way, 7.1's rationale sentence must become true.
- [C2] **The same defect, for ID segments: rename and section-move rewrites can write a TypeScript computed access that the pinned grammar rejects (1.4, 6.4, 6.5).**
  - 1.4 admits U+2028 and U+2029 in a segment ("no other code point (U+00A0, U+0085, and U+2028 included) belongs to either class"). It bars only the quote, escape and character-reference characters "so that every segment is spelled verbatim in every form".
  - 6.4 writes a segment that is not a TypeScript identifier as double-quoted computed access. It asserts that every rewritten spelling carries the identity's characters verbatim, "which every valid identity admits in every form (1.4, 2.4)". It also says the regeneration "cannot fail for any validation reason" and that "no refusal reason exists" for rewritten references.
  - Example: `src/app.ts` imports `specs/A.mdx` as `SPEC` and holds the marker `SPEC.a`, and the user runs `xspec rename specs/A.mdx a a<U+2028>b`. The marker must be rewritten to `SPEC["a<U+2028>b"]`, which TypeScript 5.0 rejects (verified above). The section form's re-identification writes the same spelling, and `refused-invalid-rewrite` judges MDX well-formedness and import additions only.
  - Under the 5.0 reading, no TypeScript consumer can reference such a node at all. An escape such as `\u2028` spells a `\`, which 2.4 reads verbatim and which no segment contains.
  - Needed, for example: bar U+2028 and U+2029 in ID segments (1.4; tags follow its rules), or otherwise fix the grammar question for them. Then correct 6.4's "every valid identity admits in every form" to match.

## Important
- [I1] **Ambiguity: which part of `refused-invalid-destination`'s source-collision clause does "a relocated origin's excepted" cover (6.5 "Validation and refusals"; its summary in 14)?** 6.5 reads: "or a derived path it would generate that is a discovered source's path, a relocated origin's excepted, or a directory component of one". 14 reads: "a derived path it would generate is a discovered source's path other than a relocated origin's or a directory component of one". As placed, the exception qualifies only "is a discovered source's path". There it can never apply: a derived path ends in `.md` or has a file name containing `.xspec.`, and a valid spec source's path does neither (7.1, 13.4). What it must decide is whether the origin is also exempt from "a directory component of one", and the two readings give opposite, testable outcomes.
  - The folder-flattening move shows the split. With Markdown emitted next to sources, run `xspec move a.md/b.mdx a.mdx`, where `a.md/` holds no other source. The destination's Markdown path `a.md` is a directory component of the origin's path and of no other source's.
  - Reading A (exception on equality only): the move is `refused-invalid-destination`.
  - Reading B (exception on both): the move performs. The relocation removes the origin before the finishing regeneration (13.5). The write of `a.md` then replaces a directory holding no source (13.4), and the removals of the origin's orphaned `a.md/b.*` files find nothing there (13.4: "a removal below a path a derived-file write replaced finds nothing there").
  - Two things favour Reading B. As placed, the exception can never apply, so its presence suggests it was meant to reach the directory-component alternative. And 13.4 already makes a derived-file write that replaces a directory of the origin's orphans well-defined, so Reading B needs no new rule. The wording still reads as A. The rationale in the same bullet adds a further ambiguity: "…or replacing … a directory holding a source or another derived file (13.4)". Under Reading B the directory `a.md/` does hold derived files: the origin's module and Markdown, which become orphans once the origin is relocated.
  - Needed: state the exemption's scope explicitly in both 6.5 and 14. If B is intended, say "is the path of, or a directory component of the path of, a discovered source other than a relocated origin". Also narrow the rationale's "another derived file" to "another derived path the sources would generate after the move". The Phase 6 tests and the Phase 10 implementation cannot agree on this move until the text settles it.

## Optional
- [O1] **14.10, recorded-file form: "instructing rebuilding" is the wrong correction for a rebuild-obstructing orphan.** Since round 4, 13.4 says an orphan occupying a directory component of a path the rebuild writes is left for manual deletion, because the rebuild is refused (14.22). `check` still reports that same path under condition 10's recorded-file form, and that form says it instructs rebuilding. 14 requires each error to identify its correction, so this finding names one that cannot succeed. Suggest: "…instructing rebuilding — or, for an orphan obstructing a write path (13.4, 14.22), its manual deletion".
- [O2] **14, location rule for condition 15: `import X = require(…)` under a leading `export`.** This round added "a leading `export` excluded as in 1.7" for a string-named module declaration, and the colliding-declaration clause says the same. The `import X = require(…)` form says only "by its own characters". TypeScript also admits it as `export import X = require("…")`. Whether that `export` falls inside the located range is now the one unstated case among these declaration forms. State it either way.
- [O3] **"Valid TypeScript identifier" is release-dependent within the 5 series (1.4, 4.6, 6.4).** 6.4 chooses dot access or double-quoted computed access by whether a segment is a valid TypeScript identifier. TypeScript 5.0.4 through 5.4.5 reject Unicode 15 identifier letters, for example U+1E030, U+11F04 and U+31350, that 5.9.3 accepts; I checked by parsing `SPEC.x<letter>`. An implementation that applies one release's identifier rule consistently stays valid either way. But the written bytes differ, and an implementation that mixes a later release's identifier rule with the 5.0 reading of 14.20 writes a dot access its own validation rejects. Suggest saying that the identifier judgement follows the same release reading as 14.20's well-formedness, or pinning it to what 5.0 accepts.
