## Important
- [I1] **14.10's recorded-file form keeps the 13.4 occupant exemptions on a failing workspace, but no test checks this (T12.2-4(b), T13.4-11; SPEC 14.10, 13.4).** The delta rewrote 14.10. The recorded-file form now covers only "an occupant the removal of 13.4 would remove, so neither a directory nor a discovered source". On a workspace failing `build`'s validations, the form "compares the record against the set of generated paths, the discovered sources, and each recorded path's occupant (13.4), all of which discovery, configuration, and the filesystem define on any workspace". T12.2-4(b) quotes that sentence, but its failing-workspace arm only stages orphans held by plain files. The occupant exemptions (directory, discovered source, nothing) are staged only in T13.4-11, and every T13.4-11 workspace passes validation; arm (b)'s occupant is the well-formed code source `export const n = 1`. A failing workspace is the natural home of the discovered-source exemption: a recorded Markdown path can only be a discovered *spec* source as an invalid one (no `.mdx`, 14.19), and an unparseable code source is still a discovered source (14.20 masks it, 11.6 lists it).
  - The bug that slips through: a product that takes "discovered sources" from its validated or parsed source model. It passes every current arm. On the failing state it reports a stale recorded file and tells the user to rebuild over a path the configuration has made a source, which `build` will not touch.
  - Suggested arms, beside T12.2-4(b), each run through `check`:
    1. Emission next to sources, `build` recording `specs/A.md`, then emission disabled and a spec glob `specs/*.md` added. `specs/A.md` is now a discovered spec-group file without `.mdx`. `check` exits 1 with that file's condition-19 finding and no condition-10 finding concerning `specs/A.md`.
    2. Optionally, a code-group twin whose Markdown is not well-formed TypeScript: condition 20, and again no condition 10 for that path.
    3. T13.4-11(a)'s directory occupant and (f)'s vacant path, each beside T12.2-4's unresolved `d` reference: no condition-10 finding concerning `specs/A.md`.
- [I2] **No symlink arm checks that the removal and the recorded-file form read the link itself (T13.4-11(c); SPEC 13.4, 14.10).** 13.4 (delta 85a2172) removes a recorded path's occupant "when that is anything but a directory or a discovered source — a symbolic link itself, never its target". A path holding nothing is left as it is. 14.10 reports exactly the occupants that removal would remove. So any symbolic link at a recorded, no-longer-generated path is an occupant: removed as the link, and reported. That includes a link to a directory and a broken link.
  - T13.4-11(c), the only symlink-occupant arm (T6.5-21(d) is the same shape), stages a link to an existing file outside the workspace. A product that classifies the occupant through a link-following probe sees a plain file there. Any removal that unlinks the path takes the link, not its target, so arm (c) only catches a product that deletes the target.
  - The probe 13.4 rules out goes uncaught. A link-following probe reads a link to a directory as a directory and a broken link as nothing; both are left in place and never reported. The result is a recorded orphan that `check` never reports and `build` never removes, behind clean reports.
  - T6.5-4 already stages a broken link beside a live one for exactly this reason: its broken-link arm "discriminates a product probing existence through link-following stat".
  - Suggested arms, in T13.4-11's protocol (`check`, `build`, `check`):
    1. `specs/A.md` replaced by a link to a real directory holding a file. Stage the directory once inside the workspace under no group's glob, and once outside the root. Then disable emission. The first `check` reports the recorded-file finding concerning `specs/A.md`. `build` exits 0 with the link gone and the directory and its file byte-identical. The last `check` is clean.
    2. A broken link (target absent), with the same expectations.
