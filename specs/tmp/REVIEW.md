# Review — `specs/SPEC.md` — Phase 4 re-entry from Phase 10 (SPEC-PROBLEMS.md: 6.5 file-form specifier spelling), round 3; the logged problem is resolved by 7.1, 14.19, and 6.5 as they now stand

## Critical

- [C1] 12.1, 13.4, 13.5, 14.22, 14.24; 6.4 and 6.5 (the closing guarantee, and `refused-invalid-destination`'s "a relocated origin's excepted"). **Ambiguity: the spec does not define what happens when one path a regeneration writes is an ancestor of another path that the same regeneration writes or removes, or of a discovered source.** Derived-file writes replace "whatever exists at its path", a directory included (13.4; 14.22 says "An occupant at a derived file's own path is not an error"). 13.5 leaves the order of a build's derived-file writes unpinned, and 12.1 does not order its removals against them. 14.22 is judged once, before any write, against the pre-write filesystem. 14.24 excludes "a directory component occupied by a non-directory". So nothing vets or orders a write whose path lies above another write, a removal, or a source, and the outcome depends on write order in ways no condition or exit class covers. Three reachable cases:
  - (a) **`build`, and every rename or move finishing regeneration (6.4), on a workspace that passes every validation.** Setup: spec group `specs/**/*.mdx`, `markdown: { emit: true }`, and sources `specs/guide.mdx` and `specs/guide.md/guide.mdx` in a real directory named `guide.md`. The second file is under an emit destination, not at one, so 13.4 does not exclude it. All write-path components are directories, so no 14.22 finding arises. `specs/guide.md` is `guide.mdx`'s emit destination. It is also a directory holding a discovered source, whose module `specs/guide.md/guide.xspec.ts` and Markdown `specs/guide.md/guide.md` the same build writes. If the replacement is written last, it destroys a source the build has just read and recorded, and the nested outputs with it. Graph data then does not match the sources, so `check` reports 14.10 right after a successful build. If the replacement is written first, the nested writes meet a plain file where they need a directory. That is not 14.22, which is reported "before making any write" (and 12.1 says a build that fails validation modifies nothing). It is not 14.24 either, which excludes it. So neither the exit class nor the final state is defined. The move refusals of 6.5 treat this exact outcome as unacceptable for paths a move adds: "writes then meeting a plain file where they need a directory (14.22), or replacing a source, or a directory holding a source or another derived file". Yet `build` and every finishing regeneration meet it with no refusal. 6.5's closing claim that "every other regenerated path [is] vetted by the valid-workspace precondition (14.22)" does not cover it.
  - (b) **A move 6.5 now admits.** Use the configuration of (a), and build a workspace whose only spec source is `specs/guide.md/guide.mdx`. This records `specs/guide.md/guide.xspec.ts`, its companions, and `specs/guide.md/guide.md`. Then `xspec move specs/guide.md/guide.mdx specs/guide.mdx` passes every refusal. The destination's emit destination `specs/guide.md` is a directory component only of the relocated origin's path, which `refused-invalid-destination` excepts, and the origin's old derived paths are not ones "the sources would generate after the move". The finishing regeneration then writes `specs/guide.md` over the directory that still holds the recorded derived files it must remove. 6.6's delta shows this, listing `specs/guide.md` as newly generated and the paths beneath it as removed. If the removals run first, the move succeeds. If the write runs first, each removal meets a plain file where it needs a directory, and again no condition, exit class, or final state is defined. A single folder-flattening move therefore has an unpinned outcome. The closing guarantee says these refusals and the precondition leave the regeneration nothing to fail on except a 14.24 write failure, and this case contradicts it.
  - (c) **Removal of a recorded derived path whose occupant is no longer a plain file.** Example: `specs/A.mdx` is deleted after a build, and a directory, possibly holding sources, is later created at its recorded `specs/A.md`. 12.1 removes "recorded derived files that the current sources and configuration no longer generate". Writes have 13.4's "replaces whatever exists" rule, but removals have no rule for another kind of occupant. It is open whether the removal deletes the directory and the sources in it, fails (14.24 or not), or leaves it. It is equally open whether 14.10's recorded-file form ("a recorded derived file … remaining") reports such an occupant.
  - Needed: a decision that fixes these outcomes. Possible directions include:
    - a build-level validation reporting a derived write path that is, or lies above, a discovered source, or that lies above another path the regeneration writes or removes, as 6.5 already does for paths a move adds;
    - a pinned order with a subsumption rule, for example removals before writes, and a write that replaces a directory subsuming the writes and removals beneath it;
    - removal semantics for a recorded path whose occupant is not a plain file.

    Any of these cascades into TEST-SPEC.
