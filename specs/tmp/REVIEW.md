# Review — specs/SPEC.md — Phase 10 problems file: how far 13.5's mutual exclusion reaches, and what a mutating command reports when exclusivity cannot be established

## Critical

- [C1] **13.5 states no reach for its mutual exclusion; the unresolved problems-file entry stands (SPEC-PROBLEMS.md, "SPEC 13.5: no mechanism can exclude every process…").** SPEC.md has not changed since the entry was logged, so the entry is unresolved and CRITICAL. The defect is in SPEC.md itself. 13.5 says the mutating commands "are mutually exclusive per workspace", that "a terminated holder MUST NOT block later commands", and that "All state is workspace-local". 13.4 sorts "Every file xspec writes" into derived or durable. §0 names "the files xspec writes to the workspace" as the file surface. Nothing bounds the exclusion by user, environment, host, or process namespace, so the logged reproduction violates the SPEC as written: a second `rename` exits 0 under a different temporary-directory setting while the first is held, and both are journaled. Yet the SPEC tells the Phase 10 engineer no reach the product could honor. A resolution must settle all of the following, whichever option the Driver picks:
  1. **The reach, in consumer-observable terms.** Say which pairs of mutating invocations on one workspace are guaranteed to exclude each other, and that the guarantee does not hold outside that set. The closing rationale, "so concurrency never loses a journal append or a resolution", must be bounded the same way, because outside the reach it is false. If the reach claims "per workspace", say whether one workspace reached by two paths counts as one: a symbolic link above the root, which 11.6 resolves physically, or a bind mount.
  2. **The liveness bound.** "A terminated holder MUST NOT block" needs some way to establish that the holder has terminated, and every way has a boundary. A holder's process cannot be inspected from another host, or from another process namespace such as a container sharing the workspace through a bind mount (problems file, point 5). Keep the reach inside the boundary where this MUST can be met, or bound the MUST explicitly. As written it is universal.
  3. **Where the exclusion keeps state.** Make "All state is workspace-local" (13.5), 13.4's two-class claim about "Every file xspec writes", and §0's interface sentence agree with the chosen answer. 13.4's universal claim already conflicts with 13.5's own hold file, which is neither derived nor durable. Whatever the exclusion writes needs the same scoping.
  4. **Option constraints from GOALS and the SPEC.**
     - Option (c), a loopback-network mechanism, contradicts §0 ("xspec performs no network access") and the identical GOALS bullet. It needs a Developer-approved GOALS change first.
     - Option (a) makes the reach depend on the invoking environment's temporary-directory setting. The contract must name that dependence (which invocation settings decide the reach). Otherwise neither the reach boundary nor C2's failure case has a blackbox route.
     - Option (a) also has a security cost when that location is shared with other users, as a system-wide temporary directory is. If other users can write that location, and the coordination path can be derived from the workspace's path, another local user can plant state there that the victim cannot remove. That state either reads as a live claim, refusing every mutating command as busy, or makes the location unusable (C2). Either way it is a standing denial of service that 13.5's "a terminated holder MUST NOT block" does not cover. If (a) is chosen, require that coordination state the invoking user does not control never refuses or disables its commands.
     - Option (b) cascades well beyond 13.4. 11.6's area classification currently admits only durable paths and graph data under `.xspec/`, and the inventory exists so that "an external tool never edits files xspec owns". 13.3's record and staleness comparisons are affected too. Then there is "modifying nothing": acquisition on a workspace with no `.xspec/` would create it, yet every refusal that follows acquisition must still modify nothing. That covers the busy refusal, the 12.0 argument-check and baseline usage errors, and the 13.3 gate (6.4, 10.7, 12.0, 13.3, 13.5). Finally, (b) must define the treatment of an entry whose holder cannot be judged, such as one left by another host or carried in by version control.
  5. **IMPLEMENTATION does not force the choice.** The problems file treats IMPLEMENTATION's portability and dependency rules as fixed. But IMPLEMENTATION yields to the spec ("where a choice here cannot satisfy them, the spec wins"), and it admits a dependency that has a "spec-grounded reason". So the reach is a product-scope decision (multi-user and shared workspaces versus environment-independence), bounded only by point 2. **Ambiguity:** Developer intent on that trade-off is unrecorded, so the Driver may need a ruling.

  Cascade, for awareness: TEST-SPEC T13.5-1 ("workspace byte-identical while held"), T13.5-2/-3/-7 (the -7 text assumes state "wherever in the workspace it keeps state"), P-10, and CERTIFICATIONS' lock fixtures all follow the reach that is chosen.

- [C2] **No outcome is defined when a mutating command cannot establish exclusivity for an environmental reason (13.5, 12.0, 12.7, 14.24, 14.25; the problems file's second "Decision needed" item).** 13.5 defines two failures around acquisition: the busy refusal, and a hold file that cannot be created. Both are usage errors that modify nothing. It defines no outcome when acquisition itself cannot complete. That happens when the place the exclusion keeps its state is missing, not a directory, unwritable, full, or occupied by something unusable. It also happens when an existing claim cannot be read, or its holder's liveness cannot be judged. The current text supports two conflicting readings:
  - **14.24 and 14.25.** They cover "a write [read] xspec makes … that the environment refuses", which literally includes the exclusion's own I/O. Their concerned path is workspace-relative, or in anchoring form above the root. A location outside the workspace has neither, and reporting it would need the absolute or environment-dependent content that 12.0 forbids.
  - **The engineer's interim choice.** This is a plain usage error with `code` and `path` null, by analogy with the hold file, which 14.24 carves out ("a hold file that cannot be created is the usage error of 13.5, never this condition"). No text grounds that reading for this case.

  A resolution must do all of the following:
  - name the case in 13.5, with "modifying nothing";
  - add it to 12.0's exit-class-2 enumeration, which of 13.5's failures names only "a mutating command refused because another is running (13.5)", and to the class-2 precedence ("first the exclusivity and hold-file errors of 13.5");
  - fix its form in 12.7's error document: code and concerned path, or both `null`;
  - if it takes a stable code, add the code to 14's exhaustive list ("Stable codes cover exactly these conditions … and no more");
  - carve it out of 14.24 and 14.25 as the hold file is, or make it one of them with a defined concerned path;
  - give it a blackbox route. Under option (b), the workspace permission staging of 14.24 applies. Under option (a), the contract must identify a location the harness can make unusable, or the requirement is untestable.

  Also decide whether a consumer can tell this case from the busy refusal. Without a decision, both are code-less exit-2 errors with unpinned messages, though one is transient (a retry succeeds) and the other persistent (a retry cannot help). 14's rationale for code-less usage errors, that they describe "the invocation the consuming tool itself composed", fits neither: both report workspace or environment state.

- [C3] **13.5's acquisition point leaves the discovered set unprotected, so the stated guarantee "the workspace it validates is the one it rewrites" does not hold, and a discovered source absent at its read has no defined outcome (13.5, 14.25, 6.4).** 13.5 says a mutating command acquires exclusivity "once its configuration is loaded and its sources discovered … and before every later check and read". Discovery, a directory read, therefore happens outside the exclusion. Concrete interleaving:
  1. Holder A is running `move specs/A.mdx specs/sub/A.mdx`, and the moved file references `x`. Before A's relocation write, command B (`rename specs/X.mdx x y`) discovers `{specs/A.mdx, specs/X.mdx}`. Discovery needs no exclusivity, so nothing stops it here.
  2. A completes its writes and terminates.
  3. B acquires exclusivity.
  4. B validates and rewrites over its stale set. It reads `specs/A.mdx`, which no longer exists. No section defines that read: 14.25 says "nonexistence is never this condition — an absent object reads as its own section states", and none states it for a discovered source, while 14.20 covers only refused content. B never sees `specs/sub/A.mdx`, so that file's reference to `x` is left unresolved once B journals the mapping.

  That contradicts 6.4's "the operation only ever rewrites a valid workspace" and "Every rewritten reference resolves by construction". It also breaks the identity continuity that the exclusion exists to protect. The behavior in this interleaving is ambiguous, so the SPEC must state:
  - which discovered set a mutating command validates and rewrites, for example the set current once exclusivity is held;
  - how that fits the class-2 precedence of 12.0, where a discovery-dependent configuration error (a file matched by both a spec and a code group, 14.14) must still precede the busy refusal.

  The same undefined read also meets non-mutating commands, which 13.5 explicitly lets run concurrently with a relocation ("All other commands may run concurrently, with last-write-wins per file"). It meets 11.2's consumers as well: they are built for a workspace that is "mid-edit", where an editor can delete a file between discovery and read. So the SPEC should give a discovered source that is absent at its read a defined reading, for example a mismatch resolved by rerunning, as 13.5 already says of derived-file inconsistency.

## Important

- [I1] **13.5's isolation MUST cannot be satisfied for overlapping workspaces, which the SPEC neither forbids nor scopes out (13.5, 7, 13.1).** 13.5 says "instances operating on different workspaces MUST NOT interfere with each other". The workspace root is the configuration file's directory (7), and nothing stops one root from lying inside another. Take a root `/p` whose spec glob `**/*.mdx` discovers `sub/x.mdx`, and an inner root `/p/sub` whose configuration discovers `x.mdx`. That is two workspaces sharing one source. Each workspace's `build` writes `/p/sub/x.xspec.ts` (13.1) with different content, because the module carries workspace-relative source paths (4, 4.4). Each therefore overwrites the other's module, and the other workspace's `check` then reports it stale (14.10). A `rename` journaled in one workspace is manual restructuring in the other (6.7), even when the two run one after the other. Nothing excludes concurrent `rename`/`move` runs in the two workspaces from each other, so they can lose an update to the shared file. Because the problems-file fix rewrites this very sentence, also bound the isolation guarantee: limit it to workspaces that share no discovered source and no derived path, or define overlap and its outcome. As written, a test built from the MUST's plain words fails against every product.

## Optional

- [O1] **Modularity (PROCESS SHOULD: break loosely coupled components into their own modules).** SPEC.md is one file of about 244 KB, with no `specs/modules/`. PROCESS explains that modules exist "because they keep individual file sizes down", and at this size every reader must page through the file in pieces. The loosest candidates are §10 (Review: strategies, statuses, items) and §11.3–11.6 (the per-file query surfaces). However, every module may use only the contract SPEC.md defines, and these sections lean on cross-cutting rules: the 13.3 gate, the 12.0 precedence, 13.5, and 14. A split therefore needs those rules stated once in the core as contract. That is a larger restructuring than this refinement, and it would shift TEST-SPEC's section citations, so the Driver may reasonably defer it.
