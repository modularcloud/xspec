# Review — specs/SPEC.md — Phase 4 jump-back from Phase 10 (SPEC-PROBLEMS: 6.5 file-form specifiers no literal can spell), round 2

The logged problem is resolved. 7.1 and 14.19 now bar `"`, `'`, `\`, U+000A, and U+000D from spec-source paths, and 6.5 refuses such a destination or created target file as `refused-invalid-destination`. Every canonical spelling a rewrite or addition writes is therefore made of `..`, `/`, `./`, `.xspec`, and path segments free of those characters. That is a well-formed ECMAScript 2024 and TypeScript literal in either quote style, with the same value read verbatim or by TypeScript. The findings below are other defects, most of them in the move/derived-path area that round 1's C2 fix touched.

## Critical

- [C1] **6.5 "Validation and refusals": a move that adds an emit destination over a discovered code source is not refused. It hides that source and overwrites it, which contradicts 6.2 and 6.5.** Round 1 handled one direction of emit-destination changes: the vacated one (`refused-exposed-derived-file`). It also handled the module-linking half of the added one (the last clause of `refused-invalid-destination`). It did not handle the discovery half of the added one. While emission is enabled, a file-form destination or a created target file adds an emit destination (7.3). Whatever that path holds is then excluded from every group (13.4), and the finishing regeneration replaces it (13.4; 14.22: "An occupant at a derived file's own path is not an error"). A code source can occupy that path, because a code glob may match a `.md` name, which parses as plain TypeScript (14.20: "any other name as plain TypeScript"). Example: `specs: {s: ["specs/*.mdx"]}`, `code: {c: ["specs/B.md"]}`, `markdown: {emit: true}`, and a code source `specs/B.md` holding valid TypeScript. Then `xspec move specs/A.mdx specs/B.mdx` passes every check. No glob matches the vacated `specs/A.md`, so `refused-exposed-derived-file` does not apply. Its finishing regeneration drops `specs/B.md`'s whole-file location and named units from the graph, removing coverage and occurrences that went through them, and overwrites the file with A's Markdown. The same happens for `xspec move specs/A.mdx#x specs/B.mdx#x` when that creates `specs/B.mdx`. This contradicts 6.2 ("the file form of `xspec move` [is] pure: [it changes] only identities and reference spellings") and 6.5's own rationale ("a move never takes a node out of the workspace"; code locations are graph nodes, 5.1). No listed reason covers it: `refused-destination-exists` judges only the destination path, and `refused-invalid-destination` judges only directory components and module-linking designation. So a product can satisfy neither the reason list nor purity. Needed: a refusal for a move that would add an emit destination currently holding an occupant discovery yields as a source. This could be a clause of `refused-exposed-derived-file` or of `refused-invalid-destination`, stated in 6.5 and in 14's list with its concerned path. 6.5's closing guarantee should also name this property alongside "no file exposed to discovery by a vacated emit destination".
- [C2] **6.5 "Validation and refusals" and closing guarantee; 6.4: destination vetting checks only occupancy before the move, so the move's own relocation or creation can collide with a path the finishing regeneration writes.** `refused-invalid-destination` checks directory components "occupied by anything other than a directory", and "a nonexistent component is never a cause". 6.5 then claims that "every other regenerated path [is] vetted by the valid-workspace precondition (14.22) — so it cannot fail for any validation reason". Derived paths may legitimately be absent before a move, because the precondition is `build`'s validations, not `check`'s staleness. Two outcomes follow:
  - *The destination becomes a directory component of a regenerated path, and the regeneration fails.* Example: `markdown: {emit: true, outDir: "gen.mdx"}` (a valid outDir, 7.3), spec globs `*.mdx` and `specs/*.mdx`, and emission not yet run. `xspec move specs/A.mdx gen.mdx` passes every check: the destination's own emit destination `gen.mdx/gen.md` has only the component `gen.mdx`, which does not exist. After the relocation that component is a plain file. The finishing regeneration's writes to `gen.mdx/gen.md` and `gen.mdx/specs/…` are then obstructed. That is condition 22 among `build`'s validations (13.3), which is exactly the failure 6.4 and 6.5 say cannot happen. The section form behaves the same way when it creates `gen.mdx`.
  - *The destination lies beneath a derived-file path the regeneration writes, and the moved source is destroyed.* Example: a spec glob `specs/**/*.mdx`, a spec source `specs/B.mdx`, and `xspec move specs/A.mdx specs/B.xspec.ts/A.mdx` before `specs/B.xspec.ts` has been generated. The destination is discoverable, because its file name carries no `.xspec.` (13.4). With emission enabled, `specs/B.md/A.mdx` works the same way. The relocation creates a directory at B's derived path. The regeneration then "replaces whatever occupies the path" (13.4, 14.22), deleting the relocated source. Alternatively it meets a write failure. Which one happens depends on the unpinned order of derived-file writes (13.5). This contradicts 6.2's purity and "a move never takes a node out of the workspace".

  Needed: a refusal, plausibly under `refused-invalid-destination` in 6.5 and 14, for a destination or created target path that equals, lies beneath, or is a directory component of a path the post-move regeneration writes. That covers every source's generated module, companions, and emit destination after the move, and the graph-data area. The closing guarantee should be restated to match. (The second case can also be set up by hand for `build`: a source authored under a directory named like an absent derived path. 12.1/13.4 then have `build` replace that directory and the source in it, in an unpinned write order. The Driver may want one rule that settles both.)
- [C3] **12.0 (fifth bullet, "Arguments that name requirement nodes…") contradicts 7.1/14.19. It claims discovered paths never contain `\`.** 12.0 says "`./specs/A.mdx`, `specs//A.mdx`, and `specs\A.mdx` name or match no discovered file, whose paths carry no `.` or `..` segment, doubled separator, or `\` (1.5, 7)". Neither citation supports the `\` part. 7 derives only "no `.`, `..`, or empty segment", and 1.5 fixes only the separator. Round 1's 14.19 now explicitly reports "a spec-group file … whose workspace-relative path contains … `\`", which is a discovered file carrying `\`. Code-source paths may carry `\` validly on platforms whose entry names admit it. By the byte-wise rule stated in the same bullet (and 11.4's membership rule), `xspec view 'specs\A.mdx'` names the discovered file `specs\A.mdx` when one exists: a view with its condition-19 finding, exit 1. By 12.0's rationale it names nothing: exit 2. Phase 6 cannot derive a single expectation. Needed: restate the `\` case so it does not claim discovered paths lack `\`, e.g. "`specs\A.mdx` does not name `specs/A.mdx`: `\` is an ordinary byte, never a separator".

## Optional
- [O1] **6.5 `refused-exposed-derived-file` bullet (and 14's entry).** The appositive "an occupant discovery would then yield as a source, one a configured spec or code group's glob matches (7)" can be read as making glob-matching the test. Discovery also excludes symbolic links, paths through them, `.xspec.` file names, paths under `.xspec/`, and every other emit destination (7, 13.4). A symbolic link at the vacated destination that a glob matches is not refused under "discovery would yield", but it is refused under "a glob matches". Dropping the appositive, or citing 13.4 beside 7, removes that second reading.
- [O2] **4.5, last sentence, against round 1's closed list in 4.** "Type-level references are unrestricted and record no edges" sits beside a rule that now makes an import type of a spec module (`typeof import("./A.xspec")`, a type-level construct) invalid under 14.15. The specific rule governs. Still, scoping the sentence would stop a Phase 6 author from reading the two as conflicting, e.g. "type-level uses of a spec module import's bindings are unrestricted; a module-linking form is governed by 4".
- [O3] **4, "No other construct names a module to xspec".** A dynamic `import()` whose argument is a no-substitution template literal (`` import(`./A.xspec`) ``) is not static by 2.4, so xspec does not analyze it. TypeScript tooling still resolves and types it as the spec module, like a string literal. So a code source can reach typed nodes and `text` outside 4.5's edge recording and 14.18's restrictions without any finding. The same form can also reach a derived-file path without 14.15. This contradicts nothing, because the SPEC says such imports are not analyzed. But it makes the sentence "an import declaration is the only one through which a TypeScript file consumes a spec module" hold only in xspec's reading. If the loophole is intended, say so; otherwise class a template-literal `import()` specifier like a static one.
